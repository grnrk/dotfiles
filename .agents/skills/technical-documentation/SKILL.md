---
name: technical-documentation
description: Use when creating, reviewing, rewriting, or updating technical documentation, such as README files, user guides, setup/installation/configuration instructions, API documentation, reference manuals, troubleshooting guides and other technical documentation.
---
 
Write the documentation according to the ASD-STE100 (Simplified Technical
English) standard.
 
Use clear, direct, and consistent language. Use common words where possible.
Avoid unnecessary words, ambiguity, idioms, metaphors, and unnecessarily complex
sentence structures. Use technical terms consistently.
 
Write related sentences as normal paragraphs. Do not put each sentence on a
separate line. A paragraph should normally contain several related sentences
that explain the same topic, concept, condition, or procedure. Start a new
paragraph when the subject or purpose changes.
 
Use headings to organize the documentation. Use numbered lists when the reader
must perform actions in a specific order. Use bullet lists when the order of the
items is not important. Use tables when they make structured information easier
to understand.
 
Do not turn every sentence into a separate paragraph or list item unless the
content requires it for clarity.
 
Apply ASD-STE100 to the documentation without discussing the writing standard.
Do not tell the reader that the documentation uses ASD-STE100, Simplified
Technical English, simplified English, plain English, or any other writing
standard.
 
Do not include statements such as:
  "This document was created using ASD-STE100."
  "This guide uses simple language and short instructions."
  "The following sections use simplified English."
 
Do not include commentary about the writing style, documentation process, or
language rules. The reader should see the result of the writing rules, not an
explanation of those rules. Do not add generic introductory or concluding text
merely to explain what the document contains or how it was written. Include
introductory or concluding text only when it provides useful information to the
reader.
 
Focus the documentation on the subject being documented. Preserve the technical
meaning of the source material and do not add information that is not supported
by the source material.

Identify the intended audience and their expected technical knowledge before writing. If this is unclear and would change the level of detail, terminology, or explanations, ask the user to clarify. If the context makes the audience clear, proceed without asking. State an audience assumption in the document only when it is important for the reader to understand its scope or use.

Keep README files concise. Focus on what the reader needs to get started and use the project: prerequisites, setup, configuration, common commands, and key behavior. Do not turn a README into a complete reference manual. Link to existing examples or detailed references instead of repeating them. Include edge cases and implementation details only when they are needed to use the project safely or correctly. Before finishing, remove repeated information and details that do not help the intended reader.
